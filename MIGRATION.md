# Migration to modern Ruby

## Objective and completion criteria

Port the H2 database engine in this repository to native modern Ruby. The objective remains the complete project, including its SQL behavior, storage, transactions, tools and network services. A Ruby facade over Java, a replacement backend, or a passing subset of SQL tests does not complete the migration.

The reference is the Java tree at upstream commit `41d021b3e`, version `2.5.259-SNAPSHOT` in `h2/pom.xml`. At migration start, `h2/src/main` contains 843 Java files and `h2/src/test/org/h2/test/scripts` contains 319 SQL scripts. Keep the reference source, fixtures, resources and licensing until their replacement has equivalent evidence.

Target runtimes are MRI Ruby 3.4 and 4.0, using Ruby classes, immutable `Data` nodes, keyword arguments and `Enumerable`. Development uses Ruby 4.0.7, matching the [current stable download](https://www.ruby-lang.org/en/downloads/) at migration start. `Gemfile.lock` records dependencies. Java is only a reference/testing tool, not a runtime dependency of the gem.

Completion requires:

1. The complete SQL script corpus and relevant Java regression scenarios have Ruby equivalents with matching results, update counts, metadata, errors and transactional behavior. Unsupported cases remain explicit gaps; they are not silently skipped or reclassified as supported.
2. A Ruby implementation of MVStore and its dependencies can read, write and reopen existing H2 database files, including recovery, compression, encryption, LOBs and upgrade scenarios. Tests must cross-read and cross-write with the reference engine and exercise interrupted commits and corrupted files.
3. Transaction, locking and isolation scenarios demonstrate H2-equivalent behavior under concurrent connections and processes. Query and index behavior is verified against the reference and benchmarks.
4. Embedded APIs, SQL tools, authentication, server protocols and the web console work in Ruby. Java-specific interfaces need an explicit interoperability or Ruby adaptation decision and tests; they remain pending until resolved.
5. The packaged gem, executable, documentation and CI run on the target Ruby release lines without requiring Java for normal use. Remove obsolete build/runtime paths only when replacement coverage is complete.

## Implemented foundation

The gem loads through `require "h2"`. `H2::Database` owns a catalog of immutable table versions; `H2::Connection` owns uncommitted changes and savepoints. Each successful modifying statement publishes a new table version or adds it to a transaction. Statement failures discard their local copy. Commit checks original table versions under a database mutex. File-backed databases then persist the entire change set with native MVStore transactions before publishing the new table versions.

The SQL pipeline has a lexer, parser, immutable syntax nodes, prepared source/query plans, expression evaluation and a statement executor. Preparation resolves metadata and nested scopes independently of execution, including when the outer input is empty. Every table occurrence has separate column bindings, including self-joins. Nested scopes resolve local columns before outer columns and retain free bindings for correlation and grouped-value checks. Wildcard visibility preserves H2's handling of join columns. `H2::Result` provides column labels, initial SQL types, rows, update counts and hash enumeration. `H2::Error` exposes an H2 error code and SQL state for the implemented errors. There is no SQL `eval`, subprocess-backed engine or alternate database backend.

Current syntax and behavior:

- Unquoted uppercase identifiers, quoted identifiers, string escaping, SQL Unicode `U&` strings/identifiers and `UESCAPE`, line and nested block comments; decimal/exponent literals and hexadecimal, octal and binary integers with digit separators; hexadecimal binary `X'...'` literals with adjacent quoted parts. Unicode decoding retains isolated UTF-16 surrogates for storage.
- `SELECT` against tables or without `FROM`, single-expression `CALL`, `TABLE`, scalar and row `VALUES`, `DISTINCT`, projections, aliases, filters, `GROUP BY`, `HAVING`, `ORDER BY`, null ordering, `LIMIT`, `OFFSET`, and `FETCH FIRST/NEXT ... ROW(S) ONLY`.
- `UNION [DISTINCT]`, `UNION ALL`, `INTERSECT`, `EXCEPT` / `MINUS` across `SELECT`, `TABLE` and `VALUES`, with intersection precedence, parentheses, branch/outer pagination and output-column ordering. Detailed semantics and limits are recorded below.
- `WITH` / `WITH RECURSIVE` common table expressions with sequential/nested scopes, explicit/inferred names, repeated references and iterative recursive batches. CTE bodies can be used throughout the implemented query contexts and in saved defaults; detailed limits and evidence are recorded below.
- Inner, left/right outer, cross, comma, natural and `USING` joins, with parentheses and nested join specifications following H2's parser. Derived `SELECT`/`VALUES`/`TABLE` queries, inline `FROM VALUES` sources, table aliases and derived column lists retain separate scopes and column provenance. Qualified stars include original join columns; plain stars merge common columns in H2's order. Explicit unqualified join-column references can remain ambiguous in H2 even when `*` merges them.
- `SYSTEM_RANGE` and `GENERATE_SERIES`, with BIGINT bounds, positive/negative steps and zero-step errors. Sized range enumeration supports direct `COUNT(*)` without iteration, including the original 2,111,222,334-row test. Limited scans without grouping, ordering or distinct results stream the source before materializing result rows. General joins currently use nested loops; index-based plans and broader optimizer behavior remain pending.
- Scalar and correlated subqueries in projections, predicates, `EXISTS`, `IN`/`NOT IN`, function arguments and DML expressions. Scalar evaluation caps output at two rows to detect error 90053; existence checks cap it at one. Empty single-column queries yield `nil`; multi-column queries yield immutable `H2::RowValue` instances, including rows of null fields for empty results. Bounded scans stream where the current plan permits; ordering/grouping can still materialize inputs. As in H2, derived sources, range arguments and limit/offset expressions reject outer references. Grouped correlations require referenced values to remain constant inside each group.
- `ROW(...)` and tuple constructors, named/nested ROW type declarations, field access, row equality/ordering, null tests, row-valued subqueries and H2's null handling for row membership. Immutable `H2::RowValue` objects retain values and optional descriptors; `H2::RowType` exposes ordered names, field types and initial metadata. Remaining conversion/composite metadata behavior and the documented Java defects remain open.
- Searched and simple `CASE`, including selected-result evaluation and H2's constant-prefix branch/type behavior. This does not replace the remaining general expression optimizer or complete expression/subquery SQL formatting.
- Positional `?` parameters with count checks, reusable prepared statements and copied string inputs. Literal defaults capture creation-time values. Defaults containing subqueries retain their AST and captured creation parameters, then read the current statement catalog when inserted or updated with `DEFAULT`.
- Integer arithmetic and bounds, decimal arithmetic using `BigDecimal`, comparisons, boolean three-valued logic, concatenation, `IS NULL/TRUE/FALSE`, `IS [NOT] DISTINCT FROM`, `BETWEEN`, `IN`, and `LIKE ... ESCAPE`.
- Initial `CAST` and assignment conversion for `TINYINT`, `SMALLINT`, `INTEGER`/`INT`, `BIGINT`, `NUMERIC`/`DECIMAL`/`DEC`, `REAL`, `DOUBLE`/`FLOAT`, `BOOLEAN`/`BOOL`, `VARCHAR`/`CHARACTER VARYING` and `CHAR`/`CHARACTER`; binary, UUID and initial temporal types are described below. This is not complete type-system parity; coercion, precision propagation, collations and edge cases remain to port.
- `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `ARRAY_AGG`; aggregate `DISTINCT` and `FILTER(WHERE ...)`, plus internal array aggregate ordering; `UNNEST` with padding, aliases and `WITH ORDINALITY`; initial `UPPER`/`UCASE`, `LOWER`/`LCASE`, `LENGTH`/`CHAR_LENGTH`, `ABS`, `COALESCE`, `IFNULL`, `NULLIF`, `MOD`, `OCTET_LENGTH` and `BIT_LENGTH`. `EXPLAIN` currently only formats plain `VALUES` statements.
- `CREATE TABLE [IF NOT EXISTS]`, typed columns, defaults, inline and composite primary/unique constraints, `NOT NULL`, and `CREATE TABLE ... AS` with inferred or declared types and optional `WITH NO DATA`. `DROP TABLE [IF EXISTS]` supports multiple tables and rejects remaining default-subquery dependencies with 90107. `TRUNCATE TABLE` returns the removed-row count.
- Multi-row `INSERT ... VALUES`, `INSERT ... DEFAULT VALUES` and `INSERT ... SELECT`, column lists and `DEFAULT`; scalar assignments in `UPDATE`; `DELETE ... WHERE`. Insert-select reads the original catalog before writing rows. Statements validate columns even on empty tables and enforce constraints atomically.
- Autocommit, explicit commit/rollback, named savepoints, transaction blocks and nested transaction blocks. DDL commits pending DML as in H2. Changes on untouched tables see later commits; a modified table retains its transaction-local version until commit. Concurrent writes to the same table fail at commit with code 90131. This is a transitional table-level implementation, not H2's row-level MVCC or locking behavior.
- Ruby CLI for inline SQL, SQL files and stdin, with persistent database, credentials and read-only options; gem packaging; Ruby CI matrix alongside the preserved upstream Java CI.

## Initial SQL file persistence

`H2.connect(path: ...)`, `H2::Database.new(path: ...)` and `H2::Database.open(path)` connect the SQL executor to the native MVStore. A base path gains `.mv.db`; an existing suffix is retained. Owned connections close their database, while explicit database objects support multiple connections until `close`. Database close invalidates connections, pending SQL changes are discarded, and file locks are released. Independent writable database objects for one path conflict instead of sharing a global engine registry.

`Persistence::Catalog` reads/writes H2's `table.0` metadata, administrator salt/hash records, CREATE_BUILD, table declarations, primary/unique constraints and ordinary index definitions. SQL statements are parsed into nodes; a separate SQL writer preserves quoting, precedence, subqueries, captured creation parameters, case expressions and query clauses in saved defaults. A value adapter maps the implemented scalar types and initial ROW values to typed H2 storage. Metadata supports the corresponding CACHED/MEMORY table, index and constraint forms during loading; this does not imply that every metadata statement is available as a user SQL command.

Creating a file initializes a real H2 SQL catalog. Publishing SQL changes synchronizes table rows, index entries and catalog records in one storage transaction. Integer primary-key delegates use their integer row ids; other row ids are retained across updates/deletes and new ids advance within a live table. Truncate resets generated ids. Drop removes the SQL records and data; unused raw-map descriptors may remain pending reclamation. File schemas outside the supported PUBLIC/type/metadata subset fail explicitly. Tables currently materialize on open and queries scan memory; only changed row/index values are sent to MVStore, whose dirty maps are still fully rewritten.

Existing administrators authenticate using H2's username/password UTF-16 hash and salted SHA-256 format. Authentication precedes transaction recovery; failed authentication leaves pending decisions unresolved. Non-administrator SQL file access is explicitly rejected. Full permission checking, user/role DDL, external authentication and encryption remain open. Read-only connections reject writes and do not resolve stored transactions. I/O failure after a durable commit decision can recover as committed; failed stores invalidate connections. SQL sessions continue to use table-version conflict checks (90131), buffered table copies and memory savepoints, rather than exposing full row-level SQL MVCC or SQL prepared transactions.

## Initial common table expressions

`WithQuery` and `CommonTableDefinition` nodes retain declaration order, optional column aliases and the recursive flag. `WithPlan` prepares each definition in its lexical scope and prepares the main query with the caller's outer row scope. `Queries` carries immutable CTE bindings separately from real catalog tables. Definitions cannot correlate outer row columns; the main body can. Duplicate declarations and actual duplicate output names fail before execution, including unused definitions. Supplied column aliases replace corresponding query names; extra names are ignored and missing names are inferred, matching H2. Nested scopes can replace outer CTE names. Real tables take precedence, and a qualified PUBLIC reference never resolves a CTE.

Potentially recursive definitions first prepare against VARCHAR placeholder columns and unbound parameter types, then prepare execution against their resulting columns. `UNKNOWN` is an internal preparation type, not a public SQL type. Untyped SELECT parameter columns fail with 50004/HY004 when H2 cannot establish a CTE column type; recursive arithmetic may instead infer VARCHAR. Explicit casts establish numeric metadata. JDBC reused-parameter cases verify both behaviors, null seeds and multiple recursive definitions with growing strings.

`CommonTable` evaluates the anchor and then the recursive branch against successive batches, retaining original row values without assignment conversion. The reference RecursiveIndex ignores the root set operator's distinct/removal semantics and its outer query tail: UNION, UNION ALL, EXCEPT and INTERSECT all accumulate batches, and root ordering/limits do not stop that iteration. Branch-local pagination and main-query ordering remain separate. Repeated references and recursive joins enumerate independent cursors over the current batch. State is cleared on failure. Results materialize in memory and repeated table references recompute; shared caches, spill, cancellation and resource budgets remain open. Recursive anchors that read themselves explicitly fail with 50100 rather than entering an unimplemented recursion path.

CTEs work in derived and scalar subqueries, EXISTS/IN, nested scopes, joins, CTAS, insert-select, update/delete expressions, transaction rollback and persisted dynamic defaults. The SQL writer carries CTE scope when serializing table sources and captured creation parameters, preserving qualified real-table references. CTE names never become catalog objects. IFNULL was added for the original recursive hierarchy case. Missing-table errors now distinguish an empty database (42104/42S04) from ordinary lookup (42102/42S02); DROP retains its own lookup behavior.

This ports the tested H2 query forms, not general WITH-statement DML, data-change delta tables, recursive views, all schema changes/name-binding stability, every parameter/type inference path, optimizer/EXPLAIN formatting or general recursive scope patterns. An inner CTE definition cannot read the outer recursive placeholder in the tested reference and fails lookup; nested RECURSIVE inside a recursive definition is a syntax error. A manually probed untyped JDBC VALUES-parameter recursive anchor produces a reference internal error and is outside the passing interoperability cases. No artificial iteration cap is imposed on otherwise accepted queries, so recursive predicates must terminate.

## Initial SQL set queries

`SetQuery` nodes preserve operand grouping, operator precedence and separate query tails. `SetPlan` prepares both operands, checks width and common column types, retains left-side labels and collects correlations from both branches. `RowSet` sorts SQL comparison keys and uses binary membership lookup; it handles nulls, numeric equivalence, CHAR trailing spaces, nested rows, bytes and unsigned UUIDs through the shared type system. Character comparison now follows UTF-16 code units, including supplementary characters and isolated surrogate storage. A separate general conversion path ignores assignment precision/scale so set operations retain actual numeric scales and binary lengths; fixed CHAR set values follow H2's trailing-space conversion.

`UNION`/`UNION DISTINCT` and `EXCEPT`/`MINUS` eliminate duplicate rows. `UNION ALL` appends both inputs. `INTERSECT` follows the preserved Java implementation: it tests right rows against left membership after applying eligible right-source distinct processing. Right pagination prevents that processing, and distinct source values can merge during common-type conversion; duplicates can consequently remain in the result. Generated tests exercise both cases. `INTERSECT ALL`, `INTERSECT DISTINCT`, `EXCEPT ALL` and `EXCEPT DISTINCT` remain syntax errors, matching this reference.

Ordering preserves H2's distinction between a bare integer position, a parenthesized integer constant and prepared position parameters. Set order expressions must name a left output column or use a position; unrelated expressions fail with 90068. Bound positions include null/negative values and parenthesized/unary-plus parameters. Query-tail parsing preserves inner pagination when only an outer order is supplied and rejects a second fetch clause. Scalar constant queries fold during preparation, including nested sets, null-result type, labels and cardinality errors. This fixes the earlier native constant-subquery CLI label to match JDBC.

Set queries are available in derived tables, scalar/correlated queries, EXISTS/IN, CTAS, insert-select, update expressions and saved dynamic defaults. The SQL writer retains operand parentheses, captured parameters and constant-versus-position ordering across file reopen. Parenthesized insert query sources are supported; an unparenthesized `INSERT ... VALUES ... UNION` is rejected as in Java. Width/binding/conversion checks and statement-level constraint rollback have reference cases. Both branches currently materialize before set processing, even with an outer limit. Lazy UNION ALL, external result spilling, full optimizer/plan formatting, remaining type semantics and complete metadata are pending; ordinary SELECT DISTINCT/grouping still have remaining general comparison work.

## SQL binary and UUID types

The SQL lexer/parser, type system, evaluator, parameter API and persistence adapter now support `BINARY`, `VARBINARY` / `BINARY VARYING`, `RAW`, `BYTEA`, `LONG RAW`, `LONGVARBINARY` and `UUID`. Binary values use copied, frozen ASCII-8BIT strings; ordinary text strings remain character values. `H2::UUIDValue` retains 16 immutable bytes, supports parameters, unsigned ordering and canonical text, and accepts H2's hex/hyphen/control-space text syntax. UUID SQL literals and character/binary casts preserve type identity.

Binary assignment pads fixed-width columns with zero bytes and rejects overlong input; explicit casts truncate. Comparisons, membership, null tests, grouping, distinct values, min/max, keys, concatenation, CASE/COALESCE and UTF-8 conversion have reference cases. Prepared parameters retain binary encoding. Casts and DML carry source type information so signed integer-to-binary conversions use the correct 1/2/4/8-byte widths, including insert-select, updates and saved defaults. Character lengths count UTF-16 units; binary lengths count bytes, integer octet lengths use their binary width, and UUID octet lengths are 16. Invalid type combinations fail explicitly, including on empty input for prepared binary comparisons/arithmetic and numeric aggregates.

The SQL writer saves binary defaults as hexadecimal and UUID defaults as typed literals. Existing H2 binary/UUID columns, primary/unique indexes, defaults and initial ROW values round-trip through native SQL and JDBC in all compression modes. The CLI prints top-level binary values as hexadecimal. Full precision propagation, binary functions, UUID generation, compatibility modes and the remaining type conversions/metadata are still pending.

There is another reproduced Java reference limitation: CTAS over an empty binary literal saves `BINARY VARYING(0)` in `table.0`; reopening logs error 90008 and omits that table. Native inferred binary columns use at least precision 1, producing files JDBC can reopen. Explicit user declarations with precision 0 remain invalid, and native loading rejects the invalid Java catalog rather than silently omitting its table. The reference suite asserts and reports this difference separately from ordinary persistence comparisons; the Java source remains unchanged.

## Initial SQL arrays

`element_type ARRAY` accepts bracket cardinalities in SQL: `INTEGER ARRAY[2]`, `TIME(9) ARRAY[3] ARRAY[2]`. The default maximum is 65,536, with declared limits 0–65,536. Bare ARRAY declarations fail with 42001. Immutable `ArrayValue` objects retain values and their common component type; `ArrayType` retains that type and maximum cardinality, exposes JDBC-style component names and scale 0, and participates in row/set/CASE/COALESCE conversions. Repeated suffixes, mixed-depth constructors and scalar promotion follow H2's recursive common-type rules.

`ARRAY[...]` and the original `ARRAY??(...??)` spelling construct arrays. `array[index]` / `ARRAY_GET` use one-based INTEGER indexes, propagate nulls and preserve 22034/2202E for bounds errors. Non-array input is rejected before scanning rows. Untyped constructors/access/slice/trim parameters retain H2's preparation-time 50004 errors; explicit component casts establish a type. `ARRAY(single_column_query)` supports ordering, empty results, CTEs and correlations, retains the declared query type and rejects zero/multiple-column queries with 90052. Zero-column SELECT syntax is accepted so that its consumers can validate their required width.

Ruby array parameters recursively copy strings/arrays and adapt existing scalar/date/time objects. Results expose frozen `.values` and `.element_type`; native array/row values can also bind directly. Scalar-to-array casts wrap one element. Element conversion precedes cardinality truncation during casts, so an invalid discarded element still fails. Assignments reject excess cardinality atomically. Numeric array promotion uses H2's component precision/scale rules, and decimal literal nodes preserve lexical scale through SQL formatting and saved defaults. This does not complete scalar numeric metadata or arithmetic migration.

Array equality can reject unequal lengths before examining elements. For equal lengths it retains an unknown result from nulls unless another component disproves equality. Ordering is lexicographic and stops at the first differing/unknown component. Null-safe comparisons and `ARRAY_CONTAINS` use H2's total value comparison, including conversion/short-circuit behavior and CHAR trailing-space comparisons. Group/distinct/set/key paths compare nested values, including offset-equivalent zoned components. Raw MVStore arrays now sort shorter equal prefixes first; the previous comparator reversed that order. Tests verify ordering and lookup after reopen, and JDBC cross-reads native array primary-key indexes.

`||`, `ARRAY_CAT` and `ARRAY_APPEND` support array concatenation/scalar operands and preserve null propagation with H2's conversion order. `CARDINALITY` / `ARRAY_LENGTH`, `ARRAY_MAX_CARDINALITY`, `TRIM_ARRAY`, `ARRAY_CONTAINS` and Regular-mode `ARRAY_SLICE` are implemented. Maximum cardinality comes from the declared type even for a null array. Trim rejects negative counts even when the array is null. Slice preserves lazy null handling, integer bounds and H2's null result for invalid ranges. Numeric aggregates reject arrays with 90015. Unsupported array arithmetic retains the observed 50100 constant-expression / 50000 nonconstant metadata errors.

Persistence recursively encodes array values through the existing MVStore codec. SQL catalogs, rows, primary/unique indexes, nested temporal/binary/numeric/UUID/initial ROW components, CTAS and defaults round-trip through native SQL and JDBC in all compression modes. Default serialization preserves decimal scales and component types, including integer widths used for binary conversion. Query defaults read current data after reopen and preserve captured creation parameters; dropping their source table remains a dependency error.

Window aggregates, remaining table functions, compatibility modes, complete parameter/component metadata, arbitrary named ROW declarations and the remaining type families are pending. General optimizer/EXPLAIN behavior remains partial. Original array script selections exclude INFORMATION_SCHEMA, MEMORY-table commands, script tooling, index DDL and reconnect directives.

The array oracle also reproduces a Java reference limitation: `RangeIndex.find` calls `getLong()` on a NULL index bound and raises 50000. A prepared `ARRAY(SELECT x FROM SYSTEM_RANGE(1,3) WHERE x<=?)` with a null bound exposes it. Native predicate filtering returns a typed empty array. The runner reports this difference separately, checks the native type/cardinality/value, and compares both null and non-null query parameters strictly through an equivalent VALUES source. It does not count the failed Java range case as an execution match.

## Array aggregation and UNNEST relations

Dedicated aggregate nodes retain arguments, DISTINCT, internal ordering and FILTER. `ARRAY_AGG` preserves null elements, returns SQL NULL for an empty group and enforces the 65,536-element limit. DISTINCT uses SQL total comparison and value ordering, keeps the first duplicate's order keys and preserves value order for equal sort keys. Internal ordering accepts multiple expressions, direction and NULLS FIRST/LAST; constant order expressions are evaluated during preparation and then removed. The shared total-order comparator also handles nested nulls in ordinary query ordering.

`FILTER(WHERE ...)` applies to ARRAY_AGG and the existing COUNT/SUM/AVG/MIN/MAX aggregates. It filters rows before evaluating their aggregate arguments and order keys; constant expressions still undergo H2's preparation-time validation. Grouped/HAVING, correlated scalar arguments, CTEs, CTAS, insert-select and persisted defaults have reference cases. A SELECT retains its parse-time aggregate flag even when constant CASE preparation discards the only aggregate expression. CASE preparation respects H2's branch traversal and freezes constant session-date comparisons before DDL resets the clock.

`UNNEST` expands arrays and initial ROW values one level; scalars produce one value, SQL NULL produces no values, and shorter arguments are padded with nulls. Default column names are C1, C2, etc.; WITH ORDINALITY adds INTEGER NORD starting at 1. Parentheses, source/column aliases, joins, membership subqueries and CALL UNNEST are supported. Arguments reject lateral column references, matching the reference engine. Column types come from the parser's statically known array types; untyped parameters, scalars and expressions without that static type report NULL columns even if their runtime values are non-null. NULL-typed assignment/array conversion produces null values, including CTAS over scalar UNNEST. SQL NULL declarations and casts follow that conversion behavior.

The persistence writer retains aggregate ordering/filters and UNNEST ordinality. For a NULL template it serializes an equivalent COALESCE(argument, NULL) wrapper, so captured parameters becoming SQL literals do not accidentally establish a different static type after reopen. Tests cross-write and reopen aggregate defaults, nested aggregate CTAS and unnested tables in all compression modes. Native tests also reopen captured filter/UNNEST parameters and CASE aggregate defaults.

Supporting numeric changes propagate common NUMERIC precision/scale beyond array constructors, infer initial +, -, * and / result metadata, divide exactly with H2's half-down rounding, and fold closed numeric arithmetic during preparation. This covers the tested aggregate component values and metadata; the later DECFLOAT slice below adds its arithmetic and inference. Other numeric operators/functions, REAL behavior, general optimization and full type metadata remain incomplete. Window aggregates explicitly remain unsupported (50100), as do the other table functions and general SELECT/aggregate EXPLAIN plans.

## Quantified array and query comparisons

ANY and its SOME alias, and ALL, accept arrays or subqueries with =, <>, !=, <, >, <=, >=, IS DISTINCT FROM and IS NOT DISTINCT FROM. Empty inputs yield false for ANY and true for ALL, even with a null left operand. A SQL NULL array yields NULL for either quantifier. Ordinary comparisons short-circuit decisive results and propagate unknowns; a left value containing nulls yields unknown for nonempty input. Null-safe operators compare nulls as values. Scalar right arguments become a one-element array, including a ROW as one value; this differs from UNNEST's row expansion.

Array predicates follow runtime value comparison, including the reference's directional scalar/collection conversion, nested null handling, early unequal-length equality and conversion short-circuits. For example, ROW(1)=ANY(1) fails with 22018, while 1=ANY(ROW(1)) succeeds. Row width mismatches retain 21002. Array predicates do not reject incompatible component types before inspecting an empty input; query predicates check comparable query/left types during query preparation, including on empty input. Numeric, character, binary, UUID, interval, temporal and initial nested array/ROW comparisons have generated reference cases. CHAR operands retain trailing-space comparison, including optimized query membership.

Query predicates preserve correlations, grouped-value validation, set/CTE bodies and pagination. They apply eligible distinct/sorted query processing before comparison, retaining actual values under NULL column metadata; NULL-typed assignment remains a separate conversion. Equality ANY uses H2's query membership behavior, including its unknown result for a nonempty single NULL-typed column. NOT inverts array operators/quantifiers but retains query-level negation. Formatting preserves the observed IN normalization, SOME-to-ANY normalization, ALL spacing and anonymous derived-source aliases. This does not complete general query/EXPLAIN formatting, metadata or index optimization.

Simple CASE supports comparison and IS NULL/TRUE/FALSE predicate operands, including quantified array/query comparisons, without reevaluating the CASE operand for each branch. These predicate branches retain H2's preparation/constant behavior. Literal temporal quantified defaults freeze at preparation; captured TIME parameters and predicate CASE branches can remain session-date dependent. JDBC checks move the session between +18 and -18 to verify both behaviors across a date boundary. Closed CHAR casts also retain their prepared value/type for membership comparison and labels.

The SQL writer preserves operators, quantifiers, query negation, predicate CASE branches and captured parameters. Native reopen tests and cross-engine files cover dynamic quantified defaults, nested arrays, null-safe CTAS and cross-written updates. Other CASE predicate forms, complete type metadata and conversions, compatibility modes, general optimization and query index plans remain pending.

## Initial SQL JSON

`JsonValue` retains normalized UTF-8 bytes and an immutable document tree. Object entries keep order and duplicate names; numbers keep their scale and use H2's BigDecimal representation. A native iterative parser/renderer handles deep nesting without depending on Ruby's JSON parser. It follows the preserved engine's accepted syntax, including leading zeros, raw string controls, signed Unicode-escape digits and its byte-reader behavior. Character, UTF-8 byte, UTF-16 and UTF-32 inputs have reference cases, including BOMs, surrogate pairs, CESU-8, invalid sequences and signed 32-bit scale boundaries. SQL literals escape non-ASCII and single quotes in H2's JSON spelling.

One numeric boundary depends on the reference JVM: Java 17's BigDecimal parser rejects `1e2147483648` with 22018, while Java 25 accepts it with the valid minimum scale -2147483648. Native JSON accepts that scale and renders `1E2147483648`, matching Java 25. The JSON oracle probes the actual Java SQL behavior before generating comparisons. When the JVM rejects this exact boundary, its 108 character/binary normalization, cast and predicate cases are checked separately against Ruby BigDecimal and scalar JSON expectations; they are reported as a runtime difference, never as Java matches. Unexpected probe results still fail. Other scale limits remain in strict differential comparisons.

JSON declarations default to a 1,000,000,000-byte limit and accept JSON(n) in that range. Casts/assignments reject oversized values with 22001; saved catalogs retain the declared limit. JSON literals and FORMAT JSON parse text; character casts quote text as a JSON string, while binary casts parse their bytes. Scalar booleans/numbers, UUIDs, supported datetimes and nested SQL arrays convert to JSON; timestamp text uses T. SQL NULL stays nil, while JSON null stays a non-null JsonValue. Public bindings accept JsonValue.parse(text_or_bytes); Ruby arrays continue to mean SQL arrays.

JSON_ARRAY and JSON_OBJECT retain argument order, duplicate members and NULL ON NULL/ABSENT ON NULL. Arrays default to omission, objects to inclusion. Unique-key checks traverse nested objects and reject duplicates with 90008. Object keys are checked before runtime value evaluation. A single nonconstant subquery argument to JSON_ARRAY collects all rows in query order, optionally applying FORMAT JSON; constant scalar subqueries retain H2's preparation-time cardinality errors. Decimal token spelling is retained for scale-sensitive JSON conversion. Scientific literals now infer normalized DECFLOAT values through query sources as well as direct constructors, including persisted defaults.

IS JSON / IS NOT JSON support VALUE/ARRAY/OBJECT/SCALAR and WITH/WITHOUT UNIQUE KEYS, return unknown for SQL NULL and reject unsupported input types as false/true. IS [NOT] OF(type, ...) tests SQL value-type identity. Both forms support predicate CASE branches. JSON array indexing/ARRAY_GET is one-based and returns SQL NULL for a missing element or non-array JSON value. UNNEST decomposes JSON arrays into JSON values; non-array JSON produces no rows. Static template typing remains distinct from runtime values, including constructor/FORMAT arguments with NULL metadata.

Comparison, keys, grouping/distinct/set queries, membership and min/max use normalized unsigned bytes, including scale-sensitive numeric identity. MVStore's existing JSON byte codec now connects to SQL values, arrays, catalogs and key indexes. Native and JDBC files cross-read/cross-write JSON rows, duplicate-key objects, Unicode keys, CTAS, constructor/query/predicate defaults and captured parameters in all compression modes. Standalone raw JSON keys are exercised before loading SQL, and installed CLI processes reopen dynamic JSON defaults.

Catalog interoperability includes native DECFLOAT(p) casts. Declared precision, negative scales and specials round-trip through SQL/MVStore/JDBC; finite values convert to JSON and non-finite conversion fails with 22018. The arithmetic and inference implementation is described below.

Supporting character changes measure VARCHAR/CHAR literal metadata, assignment/cast limits and padding in UTF-16 units; a truncated surrogate is retained as UTF-16 for storage. JDBC checks compare exact UTF-16 units rather than lossy UTF-8 transport. The lexer also accepts explicit L/l integer suffixes needed by original JSON casts. JSON aggregates, LOB/geometry conversions, string-helper prerequisites, compatibility modes, general EXPLAIN/optimizer behavior and complete type metadata remain pending.

## Decimal floating-point arithmetic and inference

DecfloatValue retains a normalized integer significand, signed 32-bit scale and Infinity/-Infinity/NaN values. Precision is limited to 100,000 digits after normalization. Trailing zeros are removed in one operation rather than repeated integer divisions, so exact quotients at the default precision do not require a loop per discarded digit. Text casts accept BMP Unicode decimal digits and Java's ASCII control/space trimming. ## Session date and local clock

Each connection owns a `SessionContext`; query plans, nested/recursive CTEs, casts, comparisons, set coercion, ROW field conversion and DML assignments pass it explicitly. `CURRENT_DATE`, `LOCALTIME`, `LOCALTIMESTAMP`, `CURRENT_TIME` and `CURRENT_TIMESTAMP` support optional parentheses. Clock functions remain dynamic in saved defaults, and JDBC checks cover their types, precision and scale.

The context samples statement entry/end times and captures its clock lazily when needed. A transaction retains that instant across statements; BEGIN or an unrelated SELECT does not capture it. Autocommit refreshes per statement. Commit, rollback, DDL and rollback to a savepoint reset it. An attempted rollback to a missing savepoint resets the clock before raising 90063; ordinary statement failures and creating a savepoint retain it. Ruby transaction blocks follow the same lifetime, including nested rollback. Current values share unrounded source components, so rounding LOCALTIMESTAMP across midnight does not alter CURRENT_DATE; TIME rounding clamps within its day. Two TIME operands produce a day/time interval and reject a forced year/month cast. Type checks still run for empty input, and IN compares each candidate against the left operand, preserving NULL semantics.

Preparation now folds the implemented constant temporal casts/functions, implicit COALESCE conversions and comparisons with H2's distinction between constants and session-dependent casts. Constant string-to-temporal casts and all-constant implicit conversions can capture the preparation date/zone; explicit TIME-to-TIMESTAMP or unzoned-to-zoned casts remain dynamic. Leap-second zone files and remaining timezone/platform configuration are unsupported; missing default-zone files fall back to the current host offset, while unavailable named zones fail explicitly.

Timezone data is an external compatibility boundary. The local system has tzdb 2026e and the CI runner has 2026c, while the checked JDKs have 2026b. Four generated future cases therefore differ in data, not conversion math. The harness accepts that difference only when the zero-offset data is from 2026c or later and the old one-hour offset is from an earlier release. It queries those offsets through Java SQL, checks the native SQL values/casts against an independent Ruby process using the system timezone, and reports the version difference separately instead of counting those cases as Java SQL matches. ## Initial native MVStore

`require "h2/mvstore"` exposes `H2::MVStore::Store` separately from the SQL catalog. It implements the actual H2 format 3: 4096-byte blocks, redundant checksummed headers, chunk headers/footers, page positions, page checksums and table of contents, layout/metadata maps, leaf and internal B-tree pages, signed variable-length integers, and H2's UTF-16 string encoding and ordering. String and signed 64-bit integer key/value codecs are available. Compression supports uncompressed pages, LZF and DEFLATE, including compressed node pages and large pages.

Writable stores append changed maps, synchronize the chunk, then publish and synchronize each header. They preserve roots and data of unopened maps. Close commits pending changes; rollback restores committed entries and invalidates newly created maps. Basic recovery scans complete chunks when headers are dirty and tolerates incomplete trailing chunks. Unsupported formats, encrypted files and specialized map types fail explicitly. Future write formats that declare a compatible read format can be opened read-only, without allowing native writes.

SQL storage codecs now retain type-tagged null/boolean/integer values, scaled decimals and DECFLOAT specials, REAL/DOUBLE, UTF-16 character variants, binary/UUID/JSON/geometry/Java-object bytes, temporal fields, intervals, arrays/rows, inline LOBs and external LOB references. `Value` and its payload records are immutable. This ports serialization, not the complete SQL operations or validation for those types. ENUM tag 25 retains its ordinal and tag without schema metadata; compact ordinals below 16 share the integer encoding. Row-level LOB pointers retain their ids; the stream API below can resolve external data explicitly through LOB metadata. Java-object bytes are not executed.

Registered `RowDataType` descriptors retain column counts, indexed columns, sort/null order and stored-key settings. `VersionedValueType` implements individual and bulk fast/slow encodings, current/committed values, operation/entry identifiers and the legacy operation-id prefix. Native metadata decoding uses an explicit factory whitelist. LOB metadata/reference stateless codecs now decode their payloads; unknown codec descriptors fail explicitly. Existing transaction-store maps resolve their codecs from the `_` registry; conflicting explicit codec choices fail. Raw maps still require caller-specified codecs on reopen. Map operations use their storage comparator and binary search, so equivalent numeric keys or index keys do not become separate Ruby hash entries.

Linux OFD locks conflict with Java's file locks and remain held independently for each read-only handle. The file API currently supports 64-bit Linux on x86_64/aarch64; verification covers x86_64. Other operating systems, incremental page updates, bounded caches, allocation/reclamation, compaction, full recovery/upgrades, encryption, complete SQL LOB integration/lifecycle, remaining transaction-store behavior and SQL lifecycle behavior remain open. Custom collations and several typed-key comparisons remain unsupported, including Unicode case-insensitive strings. Zoned temporal keys now compare by instant. Each opened map loads sorted entries, and a dirty map is fully rewritten. Direct raw table/index edits remain the caller's responsibility; the SQL persistence adapter maintains supported relationships itself.

## Native LOB stream storage and codecs

`H2::MVStore::StreamIdentifier` parses H2's three stream fragments: tag 0 with inline bytes, tag 1 with a data-block length/key, and tag 2 with a total length/indirect-block key. It validates tags and lengths, retains binary data and exposes length/in-place inspection without reading map blocks. `StreamStore` writes the original recursive layout, including short input reads, minimum/maximum thresholds, level promotion and final indirect identifiers. Defaults are 256 bytes and 256 KiB; the minimum may be zero. Binary identifiers are copied/frozen, and input IO objects remain open.

`StreamReader` traverses indirect identifiers with a stack and fetches only the needed blocks. Ruby `read(n)` fills across fragments; `readpartial(n)` matches the reference's single-buffer read and raises EOFError at EOF. `read` without a length returns remaining bytes, `getbyte` returns nil at EOF, and zero-length reads do not fetch blocks. Reader positions, actual skip counts, EOF and close follow the implemented stream contract; close moves to EOF. Deferred skips can bypass whole indirect/data blocks without fetching them. Missing blocks produce IOError with an MVStore error 50 as cause. Bad tags/lengths, mismatched data-block lengths and indirect cycles fail with MVStore error 6. This is an IO-like reader, not the complete Ruby IO API.

`StreamStore#put` serializes writers through one instance, allocates signed long block keys without colliding with existing entries, invokes an optional byte-count callback and removes its newly allocated blocks after input IO failures. Ruby input exceptions become IOError with their original cause. Binary key search retains the original existing/full-map search counts; signed-range midpoint arithmetic also handles negative cursors. An occupied upper endpoint raises RangeError before overwriting data. Length, in-place status, maximum reachable block key, deletion and diagnostic formatting share the identifier parser. Raw map and transaction-map `key?` support this allocator; transaction-map stream writes/removals retain commit/rollback behavior. Underlying maps still materialize their entries, and these checks do not establish bounded memory or Java read/write-count performance equivalence.

Immutable `BlobMetadata` and `BlobReference` records implement the raw LobStorageMap payloads and signed varints/fixed 64-bit hash. Metadata contains stream bytes, table id, raw byte/character count and content hash; references contain stream bytes and LOB id. Reference ordering compares id length, signed bytes, then signed LOB id, with the reference's null ordering. The `:blob_meta`, `:blob_reference` and `:null` codecs now round-trip through H2's `_` registry; their previously unsupported descriptors resolve to working codecs. Unknown descriptors still fail explicitly. Registered maps can infer these codecs when reopened by either engine.

`test/reference/stream_store.rb` and `StreamStoreOracle.java` add 1,302 strict comparisons: 357 stream scenarios with canonical identifiers, next keys, encoded block lengths/content hashes, callbacks, short reads, partial read/skip/EOF traces and deletion; 320 encoded/redecoded LOB metadata/reference vectors; and 625 signed reference-order pairs. ## Native LOB lifecycle

`H2::MVStore::LobStorage` implements physical LobStorageMap creation, temporary/permanent copies, shared references, table removal and deferred cleanup over the registered raw `lobMap`, `tempLobMap`, `lobRef` and `lobData` maps. The manager infers existing codecs, restores block/LOB allocation cursors on reopen and rejects a second active manager on the same raw store with MVStore error 103. Its operations serialize through the manager/store monitors. `Map#ceiling_key` finds remaining shared references by storage ordering, including negative legacy reference ids. Input failures and LOB-id exhaustion reclaim newly written blocks without publishing metadata or damaging previous values.

`create_blob(input, max_length: -1)` returns a typed storage `Value`, inline when its known limit fits `max_in_place` (default 256), and otherwise a database temporary reference with table id -2. Unknown lengths always use the reference path, even when their stream id is inline or empty. Known limits cap bytes without closing the source. `create_clob` reads UTF-8 or UTF-16BE/LE input incrementally, retains Java's UTF-16 unit counts and encodes UTF-8 with `?` replacement for isolated/truncated surrogates. Its inline decision uses three times the known character limit. Ruby integer arithmetic avoids signed overflow in that decision. UTF-16 byte reads may split code units; UTF-8 reads may split code points. Invalid UTF-8 and incomplete UTF-16 byte input fail with IOError. This is not a complete Java Reader/JDBC adapter.

`copy_lob(value, table_id:)` returns inline values unchanged or allocates a new external id sharing the original stream. Table ids -1/-2/-3 select the same temporary namespace; other ids create permanent metadata with a zero content hash and a count of BLOB bytes or CLOB UTF-16 units. `open(value)` supports inline/external values and ensure-close blocks; `get_input_stream(lob_id, table_id: nil)` can search temporary then permanent metadata. Missing locators raise MVStore error 50. External readers pin their opening version until close so cleanup cannot remove later blocks while a caller is still reading.

`remove_lob` records the current raw store version. Explicit `cleanup(oldest_version:)` removes queued references strictly older than that boundary, capped by active reader versions. It preserves queue eligibility without rotating a future entry ahead of an eligible one. `remove_all_for_table` handles only that table (or the whole temporary namespace), deferring its selected references while readers are active and preserving unrelated deferred removals. Reference deletion reclaims stream blocks only after the last copy disappears. `LobStorage.open(store)` ensures manager cleanup on exceptions; close closes readers, removes temporary references and finishes queued removals without closing the raw store. Callers must close the manager before closing its store. Read-only reopening leaves persistent maps unchanged.

They check 1,098 native input variants against those scenarios, including UTF-8, both UTF-16 byte orders and short reads. This implements physical LOB storage, not complete SQL LOB behavior. ## Initial native storage transactions

`H2::MVStore::TransactionStore` coordinates versioned maps with READ COMMITTED visibility, copied inputs, per-key write ownership, wait timeouts, atomic put-if-absent, try-put, row locking, numeric savepoints and rollback. It detects wait cycles and aborts the youngest transaction. A coordinator monitor serializes individual operations and whole commits; this is not a lock-free or page-concurrent implementation. Multi-map changes become visible together. `clear` is transactional and restores its partial changes when another transaction blocks a row. Transaction blocks roll back on exceptions and nonlocal exits. Other isolation levels are rejected explicitly.

The native undo codec uses H2's map-id/key/old-versioned-value records and the 40-bit operation log id. New map codecs are saved in the actual `_` registry under deterministic descriptor keys, and Java resolves them on reopen. `commit` first synchronizes an undo-log decision marker, then normalizes committed values, deletes committed tombstones, clears the log and synchronizes cleanup. Checkpoints and close preserve pending undo state. Writable initialization rolls back open leftovers, completes commit decisions, and retains prepared transactions for explicit resolution. Read-only initialization exposes committed visibility without rewriting the file. Initial prepared metadata uses the real ObjectDataType integer/string/Object[] subset; other Java object families remain unsupported and are not deserialized or executed.

Native tests cover interrupted cleanup, actual Java undo logs, independent-key writes, multimap visibility, clear failure atomicity, savepoint lock release, timeout preservation, deadlock victim selection, coordinator ownership, slot reuse/limits, prepared reopening and read-only restrictions. A prepared transaction without writes has native reopen coverage; Java equivalence for that case remains unverified. Full statement/snapshot isolation, the remaining isolation levels, all legacy/corrupt/drop-map recovery cases, rollback listeners, complete SQL transaction integration and performance equivalence remain pending.

There is an explicit reference limitation, reproduced with a Java-generated file as well as native files: `TransactionStore.init()` restores a transaction as `STATUS_COMMITTED`, but `Transaction.commit()` sets `wasActive = isActive(previousStatus)`, where `isActive` excludes `STATUS_COMMITTED`. `endLeftoverTransactions()` consequently leaves that decision unfinished.
