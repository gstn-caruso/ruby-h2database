# Migration to modern Ruby

## Objective and completion criteria

Port the H2 database engine in this repository to native modern Ruby. The objective remains the complete project, including its SQL behavior, storage, transactions, tools and network services. A Ruby facade over Java, a replacement backend, or a passing subset of SQL tests does not complete the migration.

The reference is the Java tree at upstream commit `41d021b3e`, version `2.5.259-SNAPSHOT` in `h2/pom.xml`. At migration start, `h2/src/main` contains 843 Java files and `h2/src/test/org/h2/test/scripts` contains 319 SQL scripts. Keep the reference source, fixtures, resources and licensing until their replacement has equivalent evidence.

Target runtimes are MRI Ruby 3.4 and 4.0, using Ruby classes, immutable `Data` nodes, keyword arguments and `Enumerable`. Development uses Ruby 4.0.7, matching the [current stable download](https://www.ruby-lang.org/en/downloads/) at migration start. `Gemfile.lock` records dependencies. Java is only a reference/testing tool, not a runtime dependency of the gem.

Completion requires:

1. The complete SQL script corpus and relevant Java regression scenarios have Ruby equivalents with matching results, update counts, metadata, errors and transactional behavior. Unsupported cases remain explicit gaps; they are not silently skipped or reclassified as supported.
2. A Ruby implementation of MVStore and its dependencies can read, write and reopen existing H2 database files, including recovery, compression, encryption, LOBs and upgrade scenarios. Tests must cross-read and cross-write with the reference engine and exercise interrupted commits and corrupted files.
3. Transaction, locking and isolation scenarios demonstrate H2-equivalent behavior under concurrent connections and processes. Query and index behavior is verified against the reference and benchmarks.
4. Embedded APIs, SQL tools, authentication, server protocols and the web console work in Ruby. Java-specific interfaces need an explicit interoperability or Ruby adaptation decision and tests; they remain pending until resolved.
5. The packaged gem, executable, documentation and CI run on the target Ruby release lines without requiring Java for normal use. Remove obsolete build/runtime paths only when replacement coverage is complete.

## Implemented foundation

The gem loads through `require "h2"`. `H2::Database` owns a catalog of immutable table versions; `H2::Connection` owns uncommitted changes and savepoints. Each successful modifying statement publishes a new table version or adds it to a transaction. Statement failures discard their local copy. Commit checks the original table versions under a database mutex before publishing the entire change set.

The SQL pipeline has a lexer, parser, immutable syntax nodes, prepared source/query plans, expression evaluation and a statement executor. Preparation resolves metadata and nested scopes independently of execution, including when the outer input is empty. Every table occurrence has separate column bindings, including self-joins. Nested scopes resolve local columns before outer columns and retain free bindings for correlation and grouped-value checks. Wildcard visibility preserves H2's handling of join columns. `H2::Result` provides column labels, initial SQL types, rows, update counts and hash enumeration. `H2::Error` exposes an H2 error code and SQL state for the implemented errors. There is no SQL `eval`, subprocess-backed engine or alternate database backend.

Current syntax and behavior:

- Unquoted uppercase identifiers, quoted identifiers, string escaping, line and nested block comments; decimal/exponent literals and hexadecimal, octal and binary integers with digit separators.
- `SELECT` against tables or without `FROM`, `TABLE`, scalar and row `VALUES`, `DISTINCT`, projections, aliases, filters, `GROUP BY`, `HAVING`, `ORDER BY`, null ordering, `LIMIT`, `OFFSET`, and `FETCH FIRST/NEXT ... ROW(S) ONLY`.
- Inner, left/right outer, cross, comma, natural and `USING` joins, with parentheses and nested join specifications following H2's parser. Derived `SELECT`/`VALUES`/`TABLE` queries, table aliases and derived column lists retain separate scopes and column provenance. Qualified stars include original join columns; plain stars merge common columns in H2's order. Explicit unqualified join-column references can remain ambiguous in H2 even when `*` merges them.
- `SYSTEM_RANGE` and `GENERATE_SERIES`, with BIGINT bounds, positive/negative steps and zero-step errors. Sized range enumeration supports direct `COUNT(*)` without iteration, including the original 2,111,222,334-row test. Limited scans without grouping, ordering or distinct results stream the source before materializing result rows. General joins currently use nested loops; index-based plans and broader optimizer behavior remain pending.
- Scalar and correlated subqueries in projections, predicates, `EXISTS`, `IN`/`NOT IN`, function arguments and DML expressions. Scalar evaluation caps output at two rows to detect error 90053; existence checks cap it at one. Empty single-column queries yield `nil`; multi-column queries yield immutable `H2::RowValue` instances, including rows of null fields for empty results. Bounded scans stream where the current plan permits; ordering/grouping can still materialize inputs. As in H2, derived sources, range arguments and limit/offset expressions reject outer references. Grouped correlations require referenced values to remain constant inside each group.
- Initial `ROW(...)` and tuple constructors, nested row values, row equality/ordering, row null tests, row-valued subqueries and H2's null handling for row membership. `H2::RowValue#values` is immutable, including string fields; `H2::RowType#fields` contains initial field types. Full row declarations, field metadata and conversion semantics remain pending.
- Searched and simple `CASE`, including selected-result evaluation and H2's constant-prefix branch/type behavior. This does not replace the remaining general expression optimizer or complete expression/subquery SQL formatting.
- Positional `?` parameters with count checks, reusable prepared statements and copied string inputs. Literal defaults capture creation-time values. Defaults containing subqueries retain their AST and captured creation parameters, then read the current statement catalog when inserted or updated with `DEFAULT`.
- Integer arithmetic and bounds, decimal arithmetic using `BigDecimal`, comparisons, boolean three-valued logic, concatenation, `IS NULL/TRUE/FALSE`, `IS [NOT] DISTINCT FROM`, `BETWEEN`, `IN`, and `LIKE ... ESCAPE`.
- Initial `CAST` and assignment conversion for `TINYINT`, `SMALLINT`, `INTEGER`/`INT`, `BIGINT`, `NUMERIC`/`DECIMAL`/`DEC`, `REAL`, `DOUBLE`/`FLOAT`, `BOOLEAN`/`BOOL`, `VARCHAR`/`CHARACTER VARYING` and `CHAR`/`CHARACTER`. This is not complete type-system parity; coercion, precision propagation, collations and edge cases remain to port.
- `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`; aggregate `DISTINCT`; initial `UPPER`/`UCASE`, `LOWER`/`LCASE`, `LENGTH`/`CHAR_LENGTH`, `ABS`, `COALESCE`, `NULLIF` and `MOD`. `EXPLAIN` currently only formats plain `VALUES` statements.
- `CREATE TABLE [IF NOT EXISTS]`, typed columns, defaults, inline and composite primary/unique constraints, `NOT NULL`, and `CREATE TABLE ... AS` with inferred or declared types and optional `WITH NO DATA`. `DROP TABLE [IF EXISTS]` supports multiple tables, with validation before removal; `TRUNCATE TABLE` is also available.
- Multi-row `INSERT ... VALUES`, `INSERT ... DEFAULT VALUES` and `INSERT ... SELECT`, column lists and `DEFAULT`; scalar assignments in `UPDATE`; `DELETE ... WHERE`. Insert-select reads the original catalog before writing rows. Statements validate columns even on empty tables and enforce constraints atomically.
- Autocommit, explicit commit/rollback, named savepoints, transaction blocks and nested transaction blocks. DDL commits pending DML as in H2. Changes on untouched tables see later commits; a modified table retains its transaction-local version until commit. Concurrent writes to the same table fail at commit with code 90131. This is a transitional table-level implementation, not H2's row-level MVCC or locking behavior.
- Ruby CLI for inline SQL, SQL files and stdin; gem packaging; Ruby CI matrix alongside the preserved upstream Java CI.

## Initial native MVStore

`require "h2/mvstore"` exposes `H2::MVStore::Store` separately from the SQL catalog. It implements the actual H2 format 3: 4096-byte blocks, redundant checksummed headers, chunk headers/footers, page positions, page checksums and table of contents, layout/metadata maps, leaf and internal B-tree pages, signed variable-length integers, and H2's UTF-16 string encoding and ordering. String and signed 64-bit integer key/value codecs are available. Compression supports uncompressed pages, LZF and DEFLATE, including compressed node pages and large pages.

Writable stores append changed maps, synchronize the chunk, then publish and synchronize each header. They preserve roots and data of unopened maps. Close commits pending changes; rollback restores committed entries and invalidates newly created maps. Basic recovery scans complete chunks when headers are dirty and tolerates incomplete trailing chunks. Unsupported formats, encrypted files and specialized map types fail explicitly. Future write formats that declare a compatible read format can be opened read-only, without allowing native writes.

SQL storage codecs now retain type-tagged null/boolean/integer values, scaled decimals and DECFLOAT specials, REAL/DOUBLE, UTF-16 character variants, binary/UUID/JSON/geometry/Java-object bytes, temporal fields, intervals, arrays/rows, inline LOBs and external LOB references. `Value` and its payload records are immutable. This ports serialization, not the complete SQL operations or validation for those types. ENUM ordinals without schema metadata decode as integers. External LOB references are not dereferenced, and Java-object bytes are not executed.

Registered `RowDataType` descriptors retain column counts, indexed columns, sort/null order and stored-key settings. `VersionedValueType` implements individual and bulk fast/slow encodings, current/committed values, operation/entry identifiers and the legacy operation-id prefix. Native metadata decoding uses an explicit factory whitelist. Known but unported stateless codecs retain descriptors and reject payload access. Existing transaction-store maps resolve their codecs from the `_` registry; conflicting explicit codec choices fail. Raw maps still require caller-specified codecs on reopen. Map operations use their storage comparator and binary search, so equivalent numeric keys or index keys do not become separate Ruby hash entries.

Linux OFD locks conflict with Java's file locks and remain held independently for each read-only handle. The file API currently supports 64-bit Linux on x86_64/aarch64; verification covers x86_64. Other operating systems, incremental page updates, bounded caches, allocation/reclamation, compaction, full recovery/upgrades, encryption, external LOB content, undo-log/transaction-store behavior and SQL lifecycle integration remain open. Custom collations and several typed-key comparisons remain unsupported, including Unicode case-insensitive strings and zoned temporal/interval keys. Each opened map loads sorted entries, and a dirty map is fully rewritten. Low-level table/index edits have JDBC round-trip evidence, but callers must maintain their consistency. `H2.connect` still uses the in-memory SQL catalog.

## Compatibility evidence

Run `bundle exec rake test` for native integration tests and original upstream expectations. The upstream adapter reads statements and expected output directly from the checked-in scripts and resolves symbolic expected errors using `h2/src/main/org/h2/api/ErrorCode.java`.

The complete upstream scripts currently executed are:

- `datatypes/int.sql` (11 statements)
- `functions/string/upper.sql` (2 statements)
- `functions/string/lower.sql` (2 statements)
- `functions/system/coalesce.sql` (1 statement)
- `functions/numeric/mod.sql` (1 statement)
- `functions/system/nullif.sql` (2 statements)

Partial coverage is explicit in `test/upstream_test.rb`: the first 6 statements in `dml/insert.sql`, the first 3 in `queries/values.sql`, the first 7 in `queries/joins.sql`, the first 7 in `queries/table.sql`, and statements 3, 5, 6, 7 plus 8 through 39 (zero-based) in `range_table.sql`. This is 78 original statements across 6 complete and 5 partial scripts. The range selection now includes nested correlation and both original prime-number queries. Range explain plans and the prepared-parameter block remain outside it. The remaining corpus is unverified, not passing. The adapter currently covers plain statements and tabular/scalar expectations, including H2's whitespace formatting of labels/values; upstream directives, prepared-parameter blocks and reconnect scenarios still need implementation.

`bundle exec rake test:reference` runs all `test/fixtures/*_reference.sql` files against a Java engine built from the checked-in source, using `test/reference/JdbcOracle.java` only as a test oracle. There are 133 statements: 62 relational cases and 71 subquery/row/conditional cases. It checks rows, column labels and type names, update counts, error codes and SQL states. It does not check complete metadata such as precision, scale, row field metadata or table origin. Java ROW type declarations are normalized to the ROW type name, numeric string formatting is normalized, and unordered result sets are compared as multisets. Fixtures use one statement per line, with explicit top-level ordering wherever row order matters. Java is not invoked by the native Ruby engine or the default test task.

Native tests additionally exercise parameter safety, static/dynamic defaults, casts, constraints, aggregate types, empty-table binding, self-joins, outer-join null extension, ambiguity, nested joins/subqueries, scope boundaries, grouped correlation, scalar cardinality, row/null behavior, CASE evaluation, derived type conversion, large ranges, atomic create/insert-select/update/delete, rollback after failures and nonlocal exits, savepoints, multi-connection visibility, lost-update rejection and atomic multitable commits. They do not prove all SQL behavior, row locks, general query performance or protocol compatibility.

MVStore native tests consume 50 primitive vectors and four checked-in binary files generated by `test/reference/MVStoreOracle.java` from the preserved Java engine. They cover all three compression modes, multiple commits, tree nodes, strings including NUL/supplementary characters and unpaired surrogates, integer boundaries, empty maps, copied inputs, rollback, read-only access, independent file locks, redundant headers, torn appends, corruption and unsupported write formats. Injected failures during chunk writing retain the previous commit; failures while publishing a header recover the synchronized new chunk. See `test/fixtures/mvstore/README.md` for fixture provenance and regeneration.

The reference task additionally runs `test/reference/mvstore.rb`: 22 cross-engine checks on newly generated files. Java reads and looks up native B-trees, Ruby modifies Java files while preserving unopened maps, Java commits further changes that Ruby can reopen, and all compression modes round-trip. It checks locks in both directions and verifies that both engines recover a native commit after the writing process is killed. These checks establish the implemented raw map subset; they do not establish general SQL `.mv.db` compatibility or full crash-safety under every failure scenario.

`test/reference/SQLStorageOracle.java` additionally supplies 156 SQL value vectors, 13 type-descriptor vectors and a binary file with an interrupted transaction. Native tests re-encode the canonical Java vectors byte-for-byte, inspect real table/catalog/index rows, preserve decimal scales and type identity, and distinguish SQL NULL from absent versioned values. They also exercise comparator-based key replacement/deletion, typed-map rollback, zero-payload NULL pages and explicit failures for unknown factories or corrupt values.

`test/reference/sql_storage.rb` adds 24 cross-engine checks. In each compression mode it generates a SQL database with 180 rows, 18 typed columns and two secondary indexes; compares native rows with JDBC values; changes a row and its text index from Ruby; queries the new index through JDBC; then reopens Java inserts/updates/deletes natively. Another scenario reserializes pending versioned values from Ruby while preserving unopened undo logs, then asks Java to complete its normal recovery and verifies the restored records. Ruby does not yet implement that transaction recovery itself.

Local verification passes 141 tests and 1321 assertions, the 133-statement SQL differential suite, 22 raw MVStore reference checks and 24 SQL storage checks on Ruby 3.4.10 and Ruby 4.0.7. The gem is built and installed into a temporary gem directory, then loaded and exercised from outside the checkout, including native MVStore persistence and typed SQL values/rows; its installed executable is checked too. The Ruby CI workflow includes independent native and reference-comparison matrices for 3.4/4.0. The Java regression workflow runs for changes under `h2/`, changes to its workflow, or manual dispatch. A workflow definition alone does not prove those remote jobs have run. Packaging and CLI checks are separate from SQL compatibility.

Every slice must retain the complete objective and add evidence for the migrated behavior. This document records progress; it is not a declaration of completion.

## Delivery cycle

Deliver coherent migration slices regularly: implement and verify behavior, update the README and this compatibility record, commit the slice, merge it into `master`, then push `master` to `origin`. Check available CI results after publishing and address failures before proceeding with further feature work. Repeat this cycle while preserving the full migration objective and making remaining gaps explicit.
