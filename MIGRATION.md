# Migration to modern Ruby

## Objective and completion criteria

Port the H2 database engine in this repository to native modern Ruby. The objective remains the complete project, including its SQL behavior, storage, transactions, tools and network services. A Ruby facade over Java, a replacement backend, or a passing subset of SQL tests does not complete the migration.

The reference is the Java tree at upstream commit `41d021b3e`, version `2.5.259-SNAPSHOT` in `h2/pom.xml`. At migration start, `h2/src/main` contains 843 Java files and `h2/src/test/org/h2/test/scripts` contains 319 SQL scripts. Keep the reference source, fixtures, resources and licensing until their replacement has equivalent evidence.

Target runtimes are MRI Ruby 3.4 and 4.0, using Ruby classes, immutable `Data` nodes, keyword arguments and `Enumerable`. Development uses Ruby 4.0.7, matching the [current stable download](https://www.ruby-lang.org/en/downloads/) at migration start. `Gemfile.lock` records dependencies. Java is only a reference/testing tool, not a runtime dependency of the gem.

Completion requires:

1. The complete SQL script corpus and relevant Java regression scenarios have Ruby equivalents with matching results, update counts, metadata, errors and transactional behavior. Unsupported cases remain explicit gaps; they are not silently skipped or reclassified as supported.
2. A Ruby implementation of MVStore and its dependencies can read, write and reopen existing H2 database files, including recovery, compression, encryption, LOBs and upgrade scenarios. Tests must cross-read and cross-write with the reference engine and exercise interrupted commits and corrupted files.
3. Transaction, locking and isolation scenarios demonstrate H2-equivalent behavior under concurrent connections and processes. Query and index behavior is verified against the reference and benchmarks.
4. Embedded APIs, SQL tools, authentication, server protocols and the web console work in Ruby. Java-specific interfaces need an explicit interoperability or Ruby adaptation decision and tests; they remain pending until resolved.
5. The packaged gem, executable, documentation and CI run on the target Ruby release lines without requiring Java for normal use. Remove obsolete build/runtime paths only when replacement coverage is complete.

## Implemented foundation

The gem loads through `require "h2"`. `H2::Database` owns a catalog of immutable table versions; `H2::Connection` owns uncommitted changes and savepoints. Each successful modifying statement publishes a new table version or adds it to a transaction. Statement failures discard their local copy. Commit checks original table versions under a database mutex. File-backed databases then persist the entire change set with native MVStore transactions before publishing the new table versions.

The SQL pipeline has a lexer, parser, immutable syntax nodes, prepared source/query plans, expression evaluation and a statement executor. Preparation resolves metadata and nested scopes independently of execution, including when the outer input is empty. Every table occurrence has separate column bindings, including self-joins. Nested scopes resolve local columns before outer columns and retain free bindings for correlation and grouped-value checks. Wildcard visibility preserves H2's handling of join columns. `H2::Result` provides column labels, initial SQL types, rows, update counts and hash enumeration. `H2::Error` exposes an H2 error code and SQL state for the implemented errors. There is no SQL `eval`, subprocess-backed engine or alternate database backend.

Current syntax and behavior:

- Unquoted uppercase identifiers, quoted identifiers, string escaping, SQL Unicode `U&` strings/identifiers and `UESCAPE`, line and nested block comments; decimal/exponent literals and hexadecimal, octal and binary integers with digit separators; hexadecimal binary `X'...'` literals with adjacent quoted parts. Unicode decoding retains isolated UTF-16 surrogates for storage.
- `SELECT` against tables or without `FROM`, single-expression `CALL`, `TABLE`, scalar and row `VALUES`, `DISTINCT`, projections, aliases, filters, `GROUP BY`, `HAVING`, `ORDER BY`, null ordering, `LIMIT`, `OFFSET`, and `FETCH FIRST/NEXT ... ROW(S) ONLY`.
- `UNION [DISTINCT]`, `UNION ALL`, `INTERSECT`, `EXCEPT` / `MINUS` across `SELECT`, `TABLE` and `VALUES`, with intersection precedence, parentheses, branch/outer pagination and output-column ordering. Detailed semantics and limits are recorded below.
- `WITH` / `WITH RECURSIVE` common table expressions with sequential/nested scopes, explicit/inferred names, repeated references and iterative recursive batches. CTE bodies can be used throughout the implemented query contexts and in saved defaults; detailed limits and evidence are recorded below.
- Inner, left/right outer, cross, comma, natural and `USING` joins, with parentheses and nested join specifications following H2's parser. Derived `SELECT`/`VALUES`/`TABLE` queries, inline `FROM VALUES` sources, table aliases and derived column lists retain separate scopes and column provenance. Qualified stars include original join columns; plain stars merge common columns in H2's order. Explicit unqualified join-column references can remain ambiguous in H2 even when `*` merges them.
- `SYSTEM_RANGE` and `GENERATE_SERIES`, with BIGINT bounds, positive/negative steps and zero-step errors. Sized range enumeration supports direct `COUNT(*)` without iteration, including the original 2,111,222,334-row test. Limited scans without grouping, ordering or distinct results stream the source before materializing result rows. General joins currently use nested loops; index-based plans and broader optimizer behavior remain pending.
- Scalar and correlated subqueries in projections, predicates, `EXISTS`, `IN`/`NOT IN`, function arguments and DML expressions. Scalar evaluation caps output at two rows to detect error 90053; existence checks cap it at one. Empty single-column queries yield `nil`; multi-column queries yield immutable `H2::RowValue` instances, including rows of null fields for empty results. Bounded scans stream where the current plan permits; ordering/grouping can still materialize inputs. As in H2, derived sources, range arguments and limit/offset expressions reject outer references. Grouped correlations require referenced values to remain constant inside each group.
- Initial `ROW(...)` and tuple constructors, nested row values, row equality/ordering, row null tests, row-valued subqueries and H2's null handling for row membership. `H2::RowValue#values` is immutable, including string fields; `H2::RowType#fields` contains initial field types. Full row declarations, field metadata and conversion semantics remain pending.
- Searched and simple `CASE`, including selected-result evaluation and H2's constant-prefix branch/type behavior. This does not replace the remaining general expression optimizer or complete expression/subquery SQL formatting.
- Positional `?` parameters with count checks, reusable prepared statements and copied string inputs. Literal defaults capture creation-time values. Defaults containing subqueries retain their AST and captured creation parameters, then read the current statement catalog when inserted or updated with `DEFAULT`.
- Integer arithmetic and bounds, decimal arithmetic using `BigDecimal`, comparisons, boolean three-valued logic, concatenation, `IS NULL/TRUE/FALSE`, `IS [NOT] DISTINCT FROM`, `BETWEEN`, `IN`, and `LIKE ... ESCAPE`.
- Initial `CAST` and assignment conversion for `TINYINT`, `SMALLINT`, `INTEGER`/`INT`, `BIGINT`, `NUMERIC`/`DECIMAL`/`DEC`, `REAL`, `DOUBLE`/`FLOAT`, `BOOLEAN`/`BOOL`, `VARCHAR`/`CHARACTER VARYING` and `CHAR`/`CHARACTER`; binary, UUID and initial temporal types are described below. This is not complete type-system parity; coercion, precision propagation, collations and edge cases remain to port.
- `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`; aggregate `DISTINCT`; initial `UPPER`/`UCASE`, `LOWER`/`LCASE`, `LENGTH`/`CHAR_LENGTH`, `ABS`, `COALESCE`, `IFNULL`, `NULLIF`, `MOD`, `OCTET_LENGTH` and `BIT_LENGTH`. `EXPLAIN` currently only formats plain `VALUES` statements.
- `CREATE TABLE [IF NOT EXISTS]`, typed columns, defaults, inline and composite primary/unique constraints, `NOT NULL`, and `CREATE TABLE ... AS` with inferred or declared types and optional `WITH NO DATA`. `DROP TABLE [IF EXISTS]` supports multiple tables and rejects remaining default-subquery dependencies with 90107. `TRUNCATE TABLE` returns the removed-row count.
- Multi-row `INSERT ... VALUES`, `INSERT ... DEFAULT VALUES` and `INSERT ... SELECT`, column lists and `DEFAULT`; scalar assignments in `UPDATE`; `DELETE ... WHERE`. Insert-select reads the original catalog before writing rows. Statements validate columns even on empty tables and enforce constraints atomically.
- Autocommit, explicit commit/rollback, named savepoints, transaction blocks and nested transaction blocks. DDL commits pending DML as in H2. Changes on untouched tables see later commits; a modified table retains its transaction-local version until commit. Concurrent writes to the same table fail at commit with code 90131. This is a transitional table-level implementation, not H2's row-level MVCC or locking behavior.
- Ruby CLI for inline SQL, SQL files and stdin, with persistent database, credentials and read-only options; gem packaging; Ruby CI matrix alongside the preserved upstream Java CI.

## Initial SQL file persistence

`H2.connect(path: ...)`, `H2::Database.new(path: ...)` and `H2::Database.open(path)` connect the SQL executor to the native MVStore. A base path gains `.mv.db`; an existing suffix is retained. Owned connections close their database, while explicit database objects support multiple connections until `close`. Database close invalidates connections, pending SQL changes are discarded, and file locks are released. Independent writable database objects for one path conflict instead of sharing a global engine registry.

`Persistence::Catalog` reads/writes H2's `table.0` metadata, administrator salt/hash records, CREATE_BUILD, table declarations, primary/unique constraints and ordinary index definitions. SQL statements are parsed into nodes; a separate SQL writer preserves quoting, precedence, subqueries, captured creation parameters, case expressions and query clauses in saved defaults. A value adapter maps the implemented scalar types and initial ROW values to typed H2 storage. Metadata supports the corresponding CACHED/MEMORY table, index and constraint forms during loading; this does not imply that every metadata statement is available as a user SQL command.

Creating a file initializes a real H2 SQL catalog. Publishing SQL changes synchronizes table rows, index entries and catalog records in one storage transaction. Integer primary-key delegates use their integer row ids; other row ids are retained across updates/deletes and new ids advance within a live table. Truncate resets generated ids. Drop removes the SQL records and data; unused raw-map descriptors may remain pending reclamation. File schemas outside the supported PUBLIC/type/metadata subset fail explicitly. Tables currently materialize on open and queries scan memory; only changed row/index values are sent to MVStore, whose dirty maps are still fully rewritten.

Existing administrators authenticate using H2's username/password UTF-16 hash and salted SHA-256 format. Authentication precedes transaction recovery; failed authentication leaves pending decisions unresolved. Non-administrator SQL file access is explicitly rejected. Full permission checking, user/role DDL, external authentication and encryption remain open. Read-only connections reject writes and do not resolve stored transactions. I/O failure after a durable commit decision can recover as committed; failed stores invalidate connections. SQL sessions continue to use table-version conflict checks (90131), buffered table copies and memory savepoints, rather than exposing full row-level SQL MVCC or SQL prepared transactions.

## Initial common table expressions

`WithQuery` and `CommonTableDefinition` nodes retain declaration order, optional column aliases and the recursive flag. `WithPlan` prepares each definition in its lexical scope and prepares the main query with the caller's outer row scope. `Queries` carries immutable CTE bindings separately from real catalog tables. Definitions cannot correlate outer row columns; the main body can. Duplicate declarations and actual duplicate output names fail before execution, including unused definitions. Supplied column aliases replace corresponding query names; extra names are ignored and missing names are inferred, matching H2. Nested scopes can replace outer CTE names. Real tables take precedence, and a qualified PUBLIC reference never resolves a CTE.

Potentially recursive definitions first prepare against VARCHAR placeholder columns and unbound parameter types, then prepare execution against their resulting columns. `UNKNOWN` is an internal preparation type, not a public SQL type. Untyped SELECT parameter columns fail with 50004/HY004 when H2 cannot establish a CTE column type; recursive arithmetic may instead infer VARCHAR. Explicit casts establish numeric metadata. JDBC reused-parameter cases verify both behaviors, null seeds and multiple recursive definitions with growing strings.

`CommonTable` evaluates the anchor and then the recursive branch against successive batches, retaining original row values without assignment conversion. The reference RecursiveIndex ignores the root set operator's distinct/removal semantics and its outer query tail: UNION, UNION ALL, EXCEPT and INTERSECT all accumulate batches, and root ordering/limits do not stop that iteration. Branch-local pagination and main-query ordering remain separate. Repeated references and recursive joins enumerate independent cursors over the current batch. State is cleared on failure. Results materialize in memory and repeated table references recompute; shared caches, spill, cancellation and resource budgets remain open. Recursive anchors that read themselves explicitly fail with 50100 rather than entering an unimplemented recursion path.

CTEs work in derived and scalar subqueries, EXISTS/IN, nested scopes, joins, CTAS, insert-select, update/delete expressions, transaction rollback and persisted dynamic defaults. The SQL writer carries CTE scope when serializing table sources and captured creation parameters, preserving qualified real-table references. CTE names never become catalog objects. IFNULL was added for the original recursive hierarchy case. Missing-table errors now distinguish an empty database (42104/42S04) from ordinary lookup (42102/42S02); DROP retains its own lookup behavior.

This ports the tested H2 query forms, not general WITH-statement DML, data-change delta tables, recursive views, all schema changes/name-binding stability, every parameter/type inference path, optimizer/EXPLAIN formatting or general recursive scope patterns. An inner CTE definition cannot read the outer recursive placeholder in the tested reference and fails lookup; nested RECURSIVE inside a recursive definition is a syntax error. A manually probed untyped JDBC VALUES-parameter recursive anchor produces a reference internal error and is outside the passing interoperability cases. No artificial iteration cap is imposed on otherwise accepted queries, so recursive predicates must terminate.

## Initial SQL set queries

`SetQuery` nodes preserve operand grouping, operator precedence and separate query tails. `SetPlan` prepares both operands, checks width and common column types, retains left-side labels and collects correlations from both branches. `RowSet` sorts SQL comparison keys and uses binary membership lookup; it handles nulls, numeric equivalence, CHAR trailing spaces, nested rows, bytes and unsigned UUIDs through the shared type system. Character comparison now follows UTF-16 code units, including supplementary characters and isolated surrogate storage. A separate general conversion path ignores assignment precision/scale so set operations retain actual numeric scales and binary lengths; fixed CHAR set values follow H2's trailing-space conversion.

`UNION`/`UNION DISTINCT` and `EXCEPT`/`MINUS` eliminate duplicate rows. `UNION ALL` appends both inputs. `INTERSECT` follows the preserved Java implementation: it tests right rows against left membership after applying eligible right-source distinct processing. Right pagination prevents that processing, and distinct source values can merge during common-type conversion; duplicates can consequently remain in the result. Generated tests exercise both cases. `INTERSECT ALL`, `INTERSECT DISTINCT`, `EXCEPT ALL` and `EXCEPT DISTINCT` remain syntax errors, matching this reference.

Ordering preserves H2's distinction between a bare integer position, a parenthesized integer constant and prepared position parameters. Set order expressions must name a left output column or use a position; unrelated expressions fail with 90068. Bound positions include null/negative values and parenthesized/unary-plus parameters. Query-tail parsing preserves inner pagination when only an outer order is supplied and rejects a second fetch clause. Scalar constant queries fold during preparation, including nested sets, null-result type, labels and cardinality errors. This fixes the earlier native constant-subquery CLI label to match JDBC.

Set queries are available in derived tables, scalar/correlated queries, EXISTS/IN, CTAS, insert-select, update expressions and saved dynamic defaults. The SQL writer retains operand parentheses, captured parameters and constant-versus-position ordering across file reopen. Parenthesized insert query sources are supported; an unparenthesized `INSERT ... VALUES ... UNION` is rejected as in Java. Width/binding/conversion checks and statement-level constraint rollback have reference cases. Both branches currently materialize before set processing, even with an outer limit. Lazy UNION ALL, external result spilling, full optimizer/plan formatting, remaining type semantics and complete metadata are pending; ordinary SELECT DISTINCT/grouping still have remaining general comparison work.

## SQL binary and UUID types

The SQL lexer/parser, type system, evaluator, parameter API and persistence adapter now support `BINARY`, `VARBINARY` / `BINARY VARYING`, `RAW`, `BYTEA`, `LONG RAW`, `LONGVARBINARY` and `UUID`. Binary values use copied, frozen ASCII-8BIT strings; ordinary text strings remain character values. `H2::UUIDValue` retains 16 immutable bytes, supports parameters, unsigned ordering and canonical text, and accepts H2's hex/hyphen/control-space text syntax. UUID SQL literals and character/binary casts preserve type identity.

Binary assignment pads fixed-width columns with zero bytes and rejects overlong input; explicit casts truncate. Comparisons, membership, null tests, grouping, distinct values, min/max, keys, concatenation, CASE/COALESCE and UTF-8 conversion have reference cases. Prepared parameters retain binary encoding. Casts and DML carry source type information so signed integer-to-binary conversions use the correct 1/2/4/8-byte widths, including insert-select, updates and saved defaults. Character lengths count UTF-16 units; binary lengths count bytes, integer octet lengths use their binary width, and UUID octet lengths are 16. Invalid type combinations fail explicitly, including on empty input for prepared binary comparisons/arithmetic and numeric aggregates.

The SQL writer saves binary defaults as hexadecimal and UUID defaults as typed literals. Existing H2 binary/UUID columns, primary/unique indexes, defaults and initial ROW values round-trip through native SQL and JDBC in all compression modes. The CLI prints top-level binary values as hexadecimal. Full precision propagation, binary functions, UUID generation, compatibility modes and the remaining type conversions/metadata are still pending.

There is another reproduced Java reference limitation: CTAS over an empty binary literal saves `BINARY VARYING(0)` in `table.0`; reopening logs error 90008 and omits that table. Native inferred binary columns use at least precision 1, producing files JDBC can reopen. Explicit user declarations with precision 0 remain invalid, and native loading rejects the invalid Java catalog rather than silently omitting its table. The reference suite asserts and reports this difference separately from ordinary persistence comparisons; the Java source remains unchanged.

## Initial SQL dates and times

`DATE`, `TIME[(scale)]` and `TIMESTAMP[(scale)]` use immutable native `DateValue`, `TimeValue` and `TimestampValue` objects. They expose calendar components, nanoseconds within the day and date/time components respectively, with canonical `.to_s` output. Pure integer Gregorian calendar conversion covers years -1,000,000,000 through 1,000,000,000, including year zero, negative years and leap-century boundaries. The runtime does not need Ruby's `date` gem or a process time-zone setting.

Typed literals and casts accept initial H2 separated/compact date/time forms, DB2-style dotted times, and space/T timestamp separators. Literal fractions truncate beyond nine digits. TIME/TIMESTAMP declarations and casts accept scales 0 through 9 and `WITHOUT TIME ZONE`; defaults are TIME(0) and TIMESTAMP(6). Assignment/casts round half-up. TIME clamps a midnight overflow to the last representable time, TIMESTAMP carries into the next date, and the maximum timestamp clamps at its year bound. DATE metadata is precision 10/scale 0; TIME/TIMESTAMP precision follows the declared scale. Literal values retain scale 9. Set coercion preserves existing nanoseconds instead of applying assignment rounding.

Supported integration includes text/component casts, temporal comparisons and ordering, min/max, keys, grouping/distinct/set queries, CASE/COALESCE, initial ROW values, prepared parameters, CTAS and saved defaults/rows/indexes. DATE and TIMESTAMP can compare after midnight promotion; DATE and TIME comparisons reject incompatible types. Ruby Date parameters map to DATE, and Ruby Time/DateTime parameters map to TIMESTAMP by copying displayed calendar/time components, without applying their UTC offset. Callers using Date/DateTime load `date` themselves. Native temporal objects bind directly. SQL serialization preserves typed literals, declared scales and EXTRACT syntax across reopen.

Initial arithmetic includes integer-day addition/subtraction for DATE/TIMESTAMP, fractional-day numeric addition/subtraction, DATE + TIME, TIMESTAMP + TIME, wrapping TIME + TIME, and TIME multiplication/division by numeric values. Fractional-day arithmetic follows the reference's whole-second rounding; initial integer-day arithmetic accepts INTEGER operands. Other integer widths for day arithmetic remain unsupported as in this snapshot. Calendar extraction, supported field aliases and truncation are described below; DAY_OF_MONTH is a function alias for DAY, not a valid EXTRACT field. Initial single-expression `CALL` supports original datatype script statements.

This is a wall-clock subset. Zoned types/text, session time-zone conversion/settings, remaining temporal conversions, zoned arithmetic, zoned current-clock functions, remaining fields/formats/conversions, metadata and optimizer behavior remain pending. Zoned declarations/text and CURRENT_TIME/CURRENT_TIMESTAMP fail explicitly with 50100; the engine does not silently choose UTC. The original temporal script selections below exclude INFORMATION_SCHEMA and ALTER TABLE behavior.

## Session date and local clock

Each connection owns a `SessionContext`; query plans, nested/recursive CTEs, casts, comparisons, set coercion, ROW field conversion and DML assignments pass it explicitly. `CURRENT_DATE`, `LOCALTIME` and `LOCALTIMESTAMP` support optional parentheses, and CURDATE(), CURTIME() and NOW() normalize to those names. LOCALTIME/LOCALTIMESTAMP accept scales 0–9, defaulting to 0/6. Labels, precision and scale match JDBC. Clock expressions remain dynamic during optimization and default serialization. Zoned CURRENT_TIME/CURRENT_TIMESTAMP, named/fixed-offset session zones and AT TIME ZONE remain for the next timezone work.

The context samples the host's local wall clock at statement entry and captures its date/time lazily when first needed. A transaction retains that snapshot across statements; BEGIN or an unrelated SELECT does not capture it prematurely. Autocommit refreshes for each statement. Commit, rollback, DDL and explicit rollback to a savepoint reset it. As in the Java source, an attempted rollback to a missing savepoint resets the clock before raising 90063; ordinary statement failures and creating a savepoint retain it. Connections have independent clocks. Ruby transaction blocks follow the same lifetime, including resetting after nested rollback. Current values share unrounded source components, so rounding LOCALTIMESTAMP across midnight does not alter CURRENT_DATE; TIME rounding clamps within its day.

TIME-to-TIMESTAMP casts and assignments now attach the session date. Comparisons and common-type conversion use that date without assignment rounding, while casts/columns apply the destination scale. Explicit year/month differences between TIME and DATE/TIMESTAMP also use the session date; unqualified datetime differences retain the reference's 1970 anchor for TIME. Two TIME operands still produce a day/time interval and reject a forced year/month cast. Captured defaults containing clock values or session-dependent casts/differences evaluate when inserted, with canonical SQL surviving cross-engine file reopen.

## Date/time arithmetic functions

`DATEADD(field, count, value)` / `TIMESTAMPADD` and `DATEDIFF(field, start, finish)` / `TIMESTAMPDIFF` support unzoned DATE/TIME/TIMESTAMP values and initial timestamp text conversion. The parser resolves static field identifiers or strings, including H2 aliases such as YY, SQL_TSI_MONTH, MS, MCS and NS; a field cannot be a bound parameter. Counts and temporal inputs can be reusable parameters. The SQL writer saves canonical field/function names in dynamic defaults, and constant functions fold for labels, types and preparation-time errors. Integer-day operator labels use H2's DATEADD representation.

DATEADD supports millennium, century, decade, year, quarter, month, week/ISO week, day and day aliases, hour, minute, second/epoch, millisecond, microsecond and nanosecond units. Calendar month/year changes clamp the day within the destination month. Subday changes preserve nanoseconds, carry between dates, wrap TIME within its day and promote DATE to TIMESTAMP; calendar fields reject TIME. Decimal counts round half-up, floating counts follow Java Math.round, and strings require integer syntax. Counts convert to signed BIGINT; all units except the three fractional-second fields additionally require INTEGER range. TIME/TIMESTAMP function metadata uses scale 9, and DATEDIFF exposes H2's BIGINT precision 64/scale 0 in the JDBC parameter checks.

DATEDIFF counts crossed unit boundaries, including reversed ranges, subsecond fields, quarters, signed-year decades/centuries/millennia and pre-epoch weeks. ISO weeks start Monday; WEEK uses the initial Sunday-based calendar. The generic Java SQL oracle pins English/US locale so this baseline is reproducible across hosts. Locale-dependent week definitions and full locale configuration remain pending. Zoned fields and values require the remaining session time-zone support and fail explicitly; the engine does not substitute UTC offsets. Week-year arithmetic is unsupported by the reference itself.

The port retains observed Java integer behavior: DATEADD calendar normalization narrows the year to 32 bits, MONTH/QUARTER differences wrap as 32-bit arithmetic before their BIGINT result, and subsecond arithmetic/differences wrap at 64 bits. Extreme negative clock normalization can produce the reference's 50000/22007 errors. Generated reference cases and native regression assertions record these boundaries rather than claiming arbitrary-precision arithmetic equivalence.

## Calendar truncation, month ends and extraction

`DATE_TRUNC(field, value)` supports microsecond, millisecond, second, minute, hour, day, ISO/local week and week-year, month, quarter, year, decade, century and millennium fields. It truncates rather than rounds, retains the DATE/TIME/TIMESTAMP value kind, and requires a datetime input type even when the value is NULL or the input relation is empty. Column expressions retain their declared scale; folded non-null TIME/TIMESTAMP constants use the reference's value scale 9. Unsupported fields such as NANOSECOND and EPOCH fail with 50100 as in Java. Period truncation handles year zero and negative years, including the reference's out-of-range errors at the minimum year.

ISO calendars use Monday and a four-day first week; the initial English/US calendar uses Sunday and a one-day first week. Week numbers, week-years and truncation can cross a calendar year, including virtual adjacent week-years outside the valid DATE year range. These computations use integer Gregorian math. The port preserves an observed Java distinction: ISO_WEEK_YEAR truncation clears the time, while local WEEK_YEAR truncation retains it, including for TIME values. Other locale calendars and compatibility modes remain pending.

`LAST_DAY(value)` returns DATE for DATE/TIMESTAMP inputs or initial H2 text parsing, including numeric/UTF-8 byte text accepted by the reference. It handles leap years, negative/zero years and both year limits. Invalid textual/TIME inputs reproduce the reference's 50000 error. Zoned values/text still require the remaining time-zone support and fail explicitly with 50100; the original LAST_DAY script combines zoned columns and remains outside the upstream selections.

`EXTRACT(field FROM value)` now accepts the reference's static field identifiers, strings and aliases. It supports all unzoned calendar/time fields, millennium/century/decade, ISO/local week/year/day fields, DOW in Regular mode, and EPOCH. Built-in field functions normalize to EXTRACT, including DAY/DAY_OF_MONTH/DAYOFMONTH, DAY_OF_WEEK/DAYOFWEEK, DAY_OF_YEAR/DAYOFYEAR, ISO_DAY_OF_WEEK, ISO_WEEK, ISO_YEAR, YEAR, MONTH, QUARTER, HOUR, MINUTE, SECOND and WEEK. Invalid field names still fail at parse time; timezone fields and mode-dependent behavior remain pending; interval extraction is described below. Fractional fields such as NANOSECOND use EXTRACT rather than an invented field function.

EPOCH returns BigDecimal seconds, preserving up to nine fractional digits and wide signed-year values. For unzoned values it uses calendar days and wall-clock nanoseconds relative to 1970-01-01, without a time-zone offset adjustment. Integer extraction metadata has precision 32/scale 0. Nonconstant EPOCH metadata is NUMERIC(28,9); folded non-null values use their actual numeric precision/scale, while NULL retains the declared type. The CLI and upstream expectation adapter print scale-zero integral decimals without an added fractional digit. Full numeric formatting/metadata behavior is still part of the remaining type-system work. Calendar functions, canonical field syntax and captured parameters survive saved dynamic defaults and file reopen.

## SQL interval values and arithmetic

The native engine implements all thirteen interval qualifiers, preserving the year/month and day/time families, sign, leading field and remaining subfields in immutable `H2::IntervalValue`. Literal parsing includes compact/partial subfields accepted by H2, external/internal signs, normalized zero and nanosecond truncation beyond nine digits. Declarations default to leading precision 2 and fractional scale 6; explicit precision is 1–18 and scale is 0–9. Literal value metadata uses precision 18/scale 9 for second-bearing qualifiers unless an explicit type is supplied. Assignment/casts round fractional seconds half-up, carry into the leading field, clamp at the maximum leading value as in the reference, and enforce the declared leading precision.

Casts convert within a family using exact month/nanosecond totals and truncate discarded units. Numeric casts, formatted/unformatted interval text, integer/decimal/float conversions, comparison, ordering, keys, grouping/distinct/set queries, CASE/COALESCE and initial ROW values have implementation/reference coverage. Comparisons reject cross-family and numeric/interval operands; set coercion accepts compatible numeric/text values without assignment rounding. Ruby callers bind native IntervalValue objects. Their `.qualifier`, `.negative`, `.leading` and `.remaining` retain the representation, `.absolute` gives signed family units, and `.to_s` emits canonical SQL text. SQL storage saves the actual interval tag/ordinal/components, and native typed-key comparison handles compatible interval qualifiers. Catalog declarations, defaults, physical indexes and rows cross-read/write with Java in every compression mode.

Interval addition/subtraction promote compatible qualifiers, numeric scaling retains the source qualifier, and interval/interval division returns NUMERIC with the reference's 40- or 64-digit scale. Numeric division requires an exact terminating decimal as in Java; zero/nonterminating numeric division reports 50000, while interval division by zero reports 22012. SUM accumulates with intermediate interval range checks; AVG widens its qualifier before averaging. Unary signs and ABS preserve interval identity. Component extraction preserves signs and the reference's 32/64-bit integer behavior. Interval EPOCH uses exact day/time nanoseconds; year/month EPOCH follows H2's 31,557,600-second years and 2,592,000-second remaining months after year/month normalization.

Unzoned DATE/TIME/TIMESTAMP subtraction produces DAY, HOUR TO SECOND or DAY TO SECOND intervals as appropriate. Explicit postfix qualifiers support calendar-month differences and precision/scale casts, including `(finish - start) YEAR TO MONTH`. Invalid qualified numeric/interval subtractions fail with 42001. Datetime plus/minus intervals is also available: month changes clamp calendar days, DATE arithmetic truncates partial days, and TIME rejects results outside its day with 22003. Mixed TIME/datetime year-month differences use the current session date as described above. Zoned operations, remaining metadata/conversions/modes, complete plan/optimizer behavior and numeric display-scale preservation remain pending.

The preserved Java snapshot reports the original difference type in result metadata even when a postfix qualifier changes the runtime value: `(DATE '2001-02-01' - DATE '2000-01-01') YEAR` has INTERVAL DAY metadata but an INTERVAL YEAR value. The native result retains this difference, and fixed/JDBC checks assert it explicitly. The reference Java source is unchanged. The upstream expectation adapter uses declared numeric scale when comparing interval ratios/casts; the public Ruby values remain BigDecimal, and full Java numeric text/scale identity is not claimed.

## Initial native MVStore

`require "h2/mvstore"` exposes `H2::MVStore::Store` separately from the SQL catalog. It implements the actual H2 format 3: 4096-byte blocks, redundant checksummed headers, chunk headers/footers, page positions, page checksums and table of contents, layout/metadata maps, leaf and internal B-tree pages, signed variable-length integers, and H2's UTF-16 string encoding and ordering. String and signed 64-bit integer key/value codecs are available. Compression supports uncompressed pages, LZF and DEFLATE, including compressed node pages and large pages.

Writable stores append changed maps, synchronize the chunk, then publish and synchronize each header. They preserve roots and data of unopened maps. Close commits pending changes; rollback restores committed entries and invalidates newly created maps. Basic recovery scans complete chunks when headers are dirty and tolerates incomplete trailing chunks. Unsupported formats, encrypted files and specialized map types fail explicitly. Future write formats that declare a compatible read format can be opened read-only, without allowing native writes.

SQL storage codecs now retain type-tagged null/boolean/integer values, scaled decimals and DECFLOAT specials, REAL/DOUBLE, UTF-16 character variants, binary/UUID/JSON/geometry/Java-object bytes, temporal fields, intervals, arrays/rows, inline LOBs and external LOB references. `Value` and its payload records are immutable. This ports serialization, not the complete SQL operations or validation for those types. ENUM ordinals without schema metadata decode as integers. External LOB references are not dereferenced, and Java-object bytes are not executed.

Registered `RowDataType` descriptors retain column counts, indexed columns, sort/null order and stored-key settings. `VersionedValueType` implements individual and bulk fast/slow encodings, current/committed values, operation/entry identifiers and the legacy operation-id prefix. Native metadata decoding uses an explicit factory whitelist. Known but unported stateless codecs retain descriptors and reject payload access. Existing transaction-store maps resolve their codecs from the `_` registry; conflicting explicit codec choices fail. Raw maps still require caller-specified codecs on reopen. Map operations use their storage comparator and binary search, so equivalent numeric keys or index keys do not become separate Ruby hash entries.

Linux OFD locks conflict with Java's file locks and remain held independently for each read-only handle. The file API currently supports 64-bit Linux on x86_64/aarch64; verification covers x86_64. Other operating systems, incremental page updates, bounded caches, allocation/reclamation, compaction, full recovery/upgrades, encryption, external LOB content, remaining transaction-store behavior and SQL lifecycle behavior remain open. Custom collations and several typed-key comparisons remain unsupported, including Unicode case-insensitive strings and zoned temporal keys. Each opened map loads sorted entries, and a dirty map is fully rewritten. Direct raw table/index edits remain the caller's responsibility; the SQL persistence adapter maintains supported relationships itself.

## Initial native storage transactions

`H2::MVStore::TransactionStore` coordinates versioned maps with READ COMMITTED visibility, copied inputs, per-key write ownership, wait timeouts, atomic put-if-absent, try-put, row locking, numeric savepoints and rollback. It detects wait cycles and aborts the youngest transaction. A coordinator monitor serializes individual operations and whole commits; this is not a lock-free or page-concurrent implementation. Multi-map changes become visible together. `clear` is transactional and restores its partial changes when another transaction blocks a row. Transaction blocks roll back on exceptions and nonlocal exits. Other isolation levels are rejected explicitly.

The native undo codec uses H2's map-id/key/old-versioned-value records and the 40-bit operation log id. New map codecs are saved in the actual `_` registry under deterministic descriptor keys, and Java resolves them on reopen. `commit` first synchronizes an undo-log decision marker, then normalizes committed values, deletes committed tombstones, clears the log and synchronizes cleanup. Checkpoints and close preserve pending undo state. Writable initialization rolls back open leftovers, completes commit decisions, and retains prepared transactions for explicit resolution. Read-only initialization exposes committed visibility without rewriting the file. Initial prepared metadata uses the real ObjectDataType integer/string/Object[] subset; other Java object families remain unsupported and are not deserialized or executed.

Native tests cover interrupted cleanup, actual Java undo logs, independent-key writes, multimap visibility, clear failure atomicity, savepoint lock release, timeout preservation, deadlock victim selection, coordinator ownership, slot reuse/limits, prepared reopening and read-only restrictions. A prepared transaction without writes has native reopen coverage; Java equivalence for that case remains unverified. Full statement/snapshot isolation, the remaining isolation levels, all legacy/corrupt/drop-map recovery cases, rollback listeners, complete SQL transaction integration and performance equivalence remain pending.
